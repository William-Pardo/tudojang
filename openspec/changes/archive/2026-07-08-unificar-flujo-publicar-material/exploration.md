### 5. Deterministic Cloud-Function IDs already do half of "duplicate-prevention" for free

`crearServicioPublishAsignacionesBatch` (`functions/academico/asignaciones.js:104-181`) derives `asignacionId = asignacion-${recursoId}-${jornadaId}` — keyed **only** on recurso+jornada (not destinatario/momento/criterio). It checks `existente.exists` and pushes to `skipped` with `reason: 'duplicado'` if so, never overwriting. Practical consequence: **calling this batch CF with `recursoIds=[oneId]`, `jornadaIds=[oneJornadaId]` already is exactly "assign one material to one class,"** and a second attempt at the same recurso+jornada pair is server-side rejected (silently skipped) regardless of what destinatario/momento you pass. This is a clean, zero-server-change fit for the new modal's CREATE path, and it independently reinforces (server-side) the UI-level duplicate-exclusion the user asked for — the client-side list-filter is still needed for good UX (so the user doesn't pick a material only to have it silently skipped), but the server already can't be fooled either way.

The single-item CF `crearServicioPublishAsignacion` (55-102) does an **unconditional** `tenant.collection('asignaciones').doc(asignacionId).set(payload)` — a true upsert. Since the client already computes the same deterministic ID (`crearClavePublicacionAsignacion` → `asignacionBaseId`, or the batch's `asignacion-${recursoId}-${jornadaId}` shape), **calling this same single CF again with the existing `id` is the natural EDIT/update path** — no new server code needed for edit either, provided the client passes the right `id`.

### 6. `actualizarAsignacion`/`eliminarAsignacion` are non-functional stubs — this is squarely in scope now

`servicios/academico/asignacionService.ts:311-325`:
```ts
export async function actualizarAsignacion(request: ActualizarAsignacionRequest): Promise<ActualizarAsignacionResponse> {
  return { ok: Boolean(request.asignacion.id) };
}
export async function eliminarAsignacion(request: EliminarAsignacionRequest): Promise<EliminarAsignacionResponse> {
  return { ok: Boolean(request.tenantId && request.asignacionId) };
}
```
Neither touches Firestore. Zero callers exist in `AsignacionesView.tsx`/its test file today. This is **documented, acknowledged debt** — the repo's own `CIERRE CENTRO DE ESTUDIOS.md:841` states verbatim that these "return simulated responses." The new design's "X remove this material" control and "Editar → persist" flow make these functions load-bearing for the first time. Good news: **Firestore rules already permit the needed direct-client writes** (`firestore.rules:278-287` — `allow create, update: if isInstructor()`, `allow delete: if isAdmin()` on `tenants/{tenantId}/asignaciones/{id}`), and this exact domain already has precedent for direct-client (non-Cloud-Function) Firestore writes: `bibliotecaService.ts` uses `setDoc`/`updateDoc` directly for `updateFicha`/`approveRecurso`, no callable involved. Recommendation: implement `eliminarAsignacion` as a real `deleteDoc` and either fix `actualizarAsignacion` similarly or (simpler, matches CF's own upsert semantics) route "edit" through the existing `publicarAsignacionFn`/`publishAsignacion` single-CF path with the same `id` — avoids adding new server logic at all.

## Approaches (edit pre-fill + dirty-checking gate on "Asignar")

1. **Snapshot + serialize + string-compare** (mirror `serializarProgramaParaCambios`/`programaTieneCambiosSinGuardar`, same file, same pattern already proven for the Programa modal) — snapshot the row config (material/destinatario/grupoObjetivo/momento/criterio/fechas/grados) when "Editar" opens the modal; on every render, compare `JSON.stringify(normalizeSort(current))` against the snapshot; disable "Asignar" when equal.
   - Pros: proven in this exact component already; trivial to extend (one more `serializarX` function); low risk of missing a field (single comparison point, not N flags to keep in sync).
   - Cons: string-compare is a slightly blunt instrument (recomputes on every render), though the existing precedent shows this is a non-issue at this component's scale.
   - Effort: Low.
2. **Per-field dirty flags** (individual `useState<boolean>` or a `Set<keyof RowConfig>` of touched fields, flipped in each field's `onChange`).
   - Pros: could show *which* field changed, if that granularity is ever needed.
   - Cons: more state to wire (one flag per field × however many fields step 2/3 have), more surface for bugs where a new field forgets to flip its flag; no existing precedent in this codebase for this pattern; no design requirement currently asks for per-field granularity.
   - Effort: Medium.

### Recommendation
**Approach 1.** It is not just cheaper — it is the *same mechanism the codebase already uses* for an analogous "was anything changed since this modal opened" gate in the very component being redesigned, a few hundred lines from where the new code will live. No behavioral reason favors per-field granularity here (the design just wants "Asignar" disabled/enabled as a single unit).

## Risks

- **Scope-creep risk if `tema` persistence is underestimated as "cosmetic re-skin."** It requires a genuine new persisted field (`JornadaInstruccion.tema?`) plus a write path, not just moving an existing value around — flagged as Open Question 1, needs a decision before sdd-design can finalize interfaces.
- **Bullets cannot reflect cancelada/reprogramada without threading `estado` through `JornadaPublicacionLocal`/`mapearJornadaAPreview`/`generarJornadasLocalesPrograma`.** Explicitly not decided here — open question for design, per instructions (should not be silently resolved either way).
- **Two vocabulary mismatches (GRUPO OBJETIVO, GRADOS) between the mock and the app's existing enums/constants** — each needs an explicit choice at design time; guessing risks building UI against a list the user didn't actually mean.
- **`eliminarAsignacion`/`actualizarAsignacion` are currently 100% non-functional** — the new "X remove" and "Editar → persist" affordances make this real backend work, not pure UI wiring; underestimating this inflates risk of the change feeling "done" in the UI but silently no-op-ing on save/delete (exactly the state today, undetected because nothing calls them yet).
- **`asignacionesPublicadas` needs a real Firestore hydration wired in** (`listarAsignacionesPorTenant`, filtered by `jornadaId`) for "Materiales asignados" to survive reloads — necessary infrastructure, not a rename.
- **Test file rewrite is substantial** (1017 lines, heavily scoped to the two flows being deleted) — budget accordingly, don't treat as incremental patching.
- **Cypress remains broken in this environment** (carried forward from every prior change this session) — E2E verification stays manual-only.
- **Adjacent unarchived change** (`asignacion-material-por-clase`) occupies related conceptual territory with no merged main spec for `academico-asignacion` — this change's proposal/spec should note it explicitly to avoid silent re-collision, not fix it (out of scope housekeeping).
