## Exploration: centro-recursos-clasificacion-manual

### Current State

**Composition.** `vistas/CentroEstudios.tsx` renders, for Admin/Editor, a 4-column grid with two embedded child views side by side: `<BibliotecaView embedded .../>` (step 1 "Conectar Drive" + step 2 "Archivos detectados") and `<AsignacionesView embedded .../>` (step 3 "Recursos aprobados" + step 4 "Programa y publicacion", both inside the *same* file/component). The two views are coupled only through a numeric `refreshTrigger`/`onRecursoAprobado` callback pair and two independent `onFlujoEstadoChange` callbacks that feed the stepper's "active" highlighting — there is **no shared React state or prop drilling of resource objects** between them. Each view independently calls `bibliotecaService.listarRecursosAprobados(tenantId)` (confirmed: `BibliotecaView.tsx:233`, `AsignacionesView.tsx:692`) and keeps its own local copy (`recursos` state in BibliotecaView, `recursosDisponibles` in AsignacionesView). This is good news for a merge: it's a duplicated-fetch problem, not a shared-state entanglement problem.

**Auto-approve, not manual classification (confirmed, matches prior investigation).** `BibliotecaView.tsx`'s per-file click handler (`indexarArchivo`, lines 464-501) calls `aprobarRecursoDetectado` (439-462), which builds a fake `FichaAcademica` via `construirFichaAutomatica` (421-426: hardcoded `disciplina: 'Taekwondo'`, `tipo` inferred from MIME, `usos: ['estudio']`, tags guessed from filename) and calls `bibliotecaService.updateFicha` then `bibliotecaService.approveRecurso` back-to-back, in one click, with zero human review. `guardarClasificacion` (662-686) and `aprobar` (688-712) are defined but **never referenced in any JSX** — confirmed by full-file read, not just grep: there are no `<input>`/`<select>` elements bound to the backing state `disciplina`/`tipo`/`uso`/`tagsTexto` (165-168, 183) anywhere in the render tree. So "revive the dead code" is not literally reviving a hidden form — there never was a rendered form, only handlers + state that anticipated one.

**The service layer already does this right.** `servicios/academico/bibliotecaService.ts` implements a clean, independently-callable state machine — `importFromDrive` (→ `borrador`) → `updateFicha` (→ `pendiente`, guards `estado !== 'borrador' && estado !== 'pendiente'`) → `approveRecurso` (→ `aprobado`, guards `estado !== 'pendiente'`) → `archiveRecurso` (→ `archivado`). `bibliotecaService.test.ts` already tests `updateFicha` and `approveRecurso` as two separate steps with correct guard-rail errors (lines 65-118). **No service-layer changes are needed to support real two-step manual classification** — only a new field to persist and UI that actually calls these two functions on two separate user actions instead of one synthetic call.

**The UI is already halfway wired for a two-step flow, just unreachable.** `obtenerEstadoFuenteDrive`/`estaArchivoAprobado` route a file row's button to `indexarArchivo` for anything not `estado === 'aprobado'`, and `aprobarRecursoDetectado` (449) already special-cases `if (recurso.estado === 'borrador' || !recurso.ficha)` — i.e., if a resource is already `pendiente` with a `ficha` set, clicking again **skips `updateFicha` and calls `approveRecurso` directly**. This exact path is already tested (`BibliotecaView.test.tsx:402-458`, "aprueba un recurso existente pendiente cuando se usa el check"). Nothing today ever leaves a resource in `pendiente`, but the plumbing for "click once to classify (if `borrador`), click again to approve (if `pendiente`)" already exists and is tested — the fix is to make the *first* click open a real form instead of auto-building the ficha.

**"Recursos aprobados" (step 3) lives inside `AsignacionesView.tsx`, not `BibliotecaView.tsx`** (`vistas/admin/AsignacionesView.tsx:1236-1443`, the `if (embedded)` branch). Confirmed structure:
- Two tabs, `tabRecursosAprobados` state (`'listos' | 'reutilizar'`), splitting `recursosDisponibles` by whether `recursoId` is in `recursosAsignadosIds` — a `Set` derived from **`asignacionesPublicadas`, which is local `useState` never populated from Firestore** (confirmed via grep: `setAsignacionesPublicadas` is only ever called from local publish-success handlers or local delete filters, lines 812, 1113, 1984, 2077 — never from a fetch effect). So "Reutilizar" is empty after every reload and only ever shows items published earlier **in the same browser session**. This matches the prior finding exactly; it's not just low-value, the tab is structurally incapable of ever being useful across a page reload as built.
- Clicking a card opens `modalRecursoAbierto` ("Preparar asignacion", lines 1360-1441): read-only "Nombre original", an input for "Titulo visible para alumno" (→ `tituloPersonalizado` state), a textarea + tag-picker for "Tags para reutilizacion" (→ `tagsAsignacion` state), and a 3-button "Aprobado para" toggle bound to `tipoDestinatario` (the *same* state the publish/lote section uses for real destinatario routing).
- Clicking "Asignar" (`asignarRecursoSeleccionado`, 959-972) does exactly one thing: `recursosLoteIds.add(recursoSeleccionado.id)`. **It reads neither `tituloPersonalizado` nor `tagsAsignacion`.** Both are silently dropped — confirmed structurally, not just anecdotally: `publicarLote` (1036-1125) builds `asignacionBase` (1060-1073) with a **hardcoded `titulo: ''`** and **no `tags` key at all**. The Cloud Function `publishAsignacionesBatch` (`functions/academico/asignaciones.js:159-170`) spreads `...asignacionBase` and only overrides `titulo: asignacionBase.titulo || recurso.nombre` — since the client always sends `''`, it **always** falls back to the raw Drive filename for every batch-published asignacion, which is the one and only publish path this embedded flow uses.
- This is architecturally unfixable in place, not just unwired: `tipoDestinatario`/`tituloPersonalizado`/`tagsAsignacion` are **single shared state values**, but `recursosLoteIds` is a `Set` that can queue *multiple different resources* for one batch publish. Even if `publicarLote` were changed to forward `tituloPersonalizado`, every resource in the batch would get the *same* title — there is no per-resource slot for it in today's data flow. This is the concrete, mechanical reason the title must be captured once per-resource at classification time (this change) rather than per-batch at publish time (today's broken attempt) — it's not just a style preference, the current design cannot represent it any other way.
- `functions/academico/asignaciones.js` and the `recursosLoteIds`/`publicarLote`/tag-filter batch machinery were added very recently by change `openspec/changes/asignacion-material-por-clase/` (dated 2026-07-04, one day before "today"). The title/tags-discard bug appears to be an oversight in that change, not previously-known debt — its `proposal.md` only discusses tag-based filtering and bulk assignment, not title capture.

**Downstream `asignacion.titulo` consumers are unaffected by this change.** `components/academico/AsignacionCard.tsx:48`, `components/academico/MaterialPreviewModal.tsx:103,134`, `components/academico/QuizView.tsx:133`, and `vistas/admin/MisClasesView.tsx:53` all read `asignacion.titulo` — a field on `AsignacionAcademica` (`models/academico/asignacion.ts:58`), which already exists and is unrelated to the new `RecursoAcademico.tituloVisible` field this change adds. This change's job is only to make sure the curated value *exists upstream* on the resource; wiring it as the default for `asignacion.titulo` at publish time is explicitly the next change's job (`grupos-publicacion-material`). None of these four files need to change for this change.

**No Firestore rules/index impact.** `firestore.rules:268-275` for `tenants/{tenantId}/recursos/{recursoId}` only checks role + tenant (`isInstructor()`/`isAdmin()` + `currentTenantId() == tenantId`) — no field-level schema validation exists, so adding an optional `tituloVisible` costs nothing there. Nothing proposed here is queried, filtered, or ordered by, so `firestore.indexes.json` needs no change either.

**Existing dead/parallel stub confirms there's no other classification UI to borrow.** `vistas/admin/AportarRecursoView.tsx` (maestro-contributes-a-resource flow) is a hardcoded demo with a fixed array and canned `ficha` per item — not routed anywhere in `App.tsx` (grep confirms zero references), not a real form either. There is genuinely no existing manual-classification form anywhere in the codebase to copy; a real one must be authored, just backed by already-correct state/handlers/service calls.

**Process/governance context (important, not just code).** The working tree currently has substantial **uncommitted** changes across every file this change must touch: `git diff --stat` shows `BibliotecaView.tsx` (+1019/-…), `AsignacionesView.tsx` (+2191/-…), `CentroEstudios.tsx` (+156), `bibliotecaService.ts` (+90), `recurso.ts` (+21), `functions/academico/asignaciones.js` (+80) all dirty against HEAD. Untracked root docs (`CIERRE CENTRO DE ESTUDIOS.md` — itself modified with staged+unstaged changes, `COORDINACION CODEX ANTIGRAVITY - CENTRO ESTUDIOS.md`, `Plan_de_Implementación_Refactor_Modal_Programa_Académico_y_Publicar_Material.md`, `docs/UX_PIPELINE_CENTRO_ESTUDIOS_DRIVE_2026-07-01.md`) show this module has been under active, disciplined, TDD-gated multi-agent (Codex + Antigravity/Gemini) development for the past ~week, with its own contract/coordination protocol. Two things stand out:
1. `docs/UX_PIPELINE_CENTRO_ESTUDIOS_DRIVE_2026-07-01.md` (4 days before "today") already describes a target **3-step** pipeline ("Conectar Drive" / "Biblioteca, clasificación y aprobación" / "Asignación académica") where step 2 explicitly states "la clasificación y aprobación se presentan como parte del mismo paso 2" — i.e., someone already documented the *intent* to unify classification+approval visually. The current 4-step code (with "Archivos detectados" and "Recursos aprobados" split) is a **regression away from** that documented intent, apparently reintroduced when the `asignacion-material-por-clase` batch-publish work landed. Moving that grid/modal out of `AsignacionesView.tsx` and into the merged resources component actually **tightens** this other contract's scope boundary rather than fighting it (it removes code from `AsignacionesView.tsx` that never conceptually belonged to "Programa academico"/"Publicar material" in the first place). ### Approaches

**Fork 1 — Classification UI: adapt existing dead code vs. build fresh**

1. **Adapt existing state/handlers, author new form JSX** — reuse `disciplina`/`tipo`/`uso`/`tagsTexto` state and `guardarClasificacion`/`aprobar` handlers already in `BibliotecaView.tsx`, add a `tituloVisible` field alongside, wrap in a real modal opened on click of a `borrador`/unclassified file.
   - Pros: Reuses logic that already matches `FichaAcademica`'s shape exactly and is already exercised indirectly via `bibliotecaService.test.ts`; smallest diff; lowest risk of introducing a new bug in the state machine.
   - Cons: Needs care wiring "which resource is the modal editing" (today `recursoSeleccionado` is implicitly "last-clicked file in the list", not modal-scoped) — a small but real refactor of that selection state.
   - Effort: Low-Medium.
2. **Build a fresh classification component, delete the old state/handlers** — new `<ClasificarRecursoModal>` with its own local state and calls into `bibliotecaService` directly.
   - Pros: Cleaner isolation, easier standalone unit tests for the modal.
   - Cons: Throws away already-correct, already-shape-matched logic for no functional gain — the old fields aren't wrong, they were just never rendered; higher effort for an equivalent result.
   - Effort: Medium-High.
   - **Recommendation: 1.** Nothing about the existing fields/handlers is broken or mis-shaped; the only gap is missing JSX and the missing `tituloVisible` field.

**Fork 2 — Where `tituloVisible` lives on the model**

1. **Top-level field on `RecursoAcademico`**, sibling to `nombre`.
   - Pros: Mirrors the existing raw/curated pairing (`nombre` vs. `tituloVisible`) at the same level; downstream consumers (this change and the future publish-default) don't need to null-check through `ficha`.
   - Cons: One more optional top-level field on an already-sizeable interface.
2. **Nested inside `FichaAcademica.tituloVisible`.**
   - Pros: Keeps everything set-during-classification in one bag alongside `tags`/`disciplina`/`tipo`.
   - Cons: Titles are about identity/display, not pedagogy — doesn't fit `ficha`'s stated purpose ("metadatos pedagógicos") as cleanly; forces `recurso.ficha?.tituloVisible` chains everywhere it's read.
   - **Recommendation: 1** (top-level), final call belongs to sdd-design/sdd-spec.

**Fork 3 — "Reutilizar" tab: delete vs. replace with real data**

1. **Delete entirely**, matching the user's stated position.
   - Pros: Removes ~60 lines of JSX plus a filter split (`recursosAprobadosListos`/`recursosAprobadosReutilizables`) and state (`tabRecursosAprobados`) that has never worked correctly (confirmed: backing `asignacionesPublicadas` is local-only, never fetched); zero backend work; no user-visible feature is actually removed since the tab has never shown real cross-session data.
   - Cons: None significant found.
   - Effort: Low.
2. **Replace with a real "reuse history"** backed by `listarAsignacionesPorTenant` (`servicios/academico/asignacionService.ts:142-147`, already exists and used by `MisClasesView`).
   - Pros: Would make "has this resource been used before" actually true.
   - Cons: Meaningfully larger scope than this change intends (new fetch effect, new per-resource usage UI, cross-referencing by `recursoId`); closer to a publish-history feature than a classification feature — better scoped to a later change if ever wanted; user already indicated the container itself adds no value.
   - **Recommendation: 1**, confirmed by code that the tab is structurally dead weight, not just low-value.

**Fork 4 — Migration for resources already approved under the old automatic flow**

1. **No backfill — optional field, lazy fallback to `nombre` everywhere it's read.**
   - Pros: Zero migration script to write/test/roll back; behavior for every existing resource is byte-for-byte identical to today (today's *only* behavior is "show `nombre`" — that's the status quo, not a regression); reversible trivially since it's an unused/absent field; no `firestore.rules` change needed (already schema-less for this collection).
   - Cons: An admin who wants a curated title on an already-approved legacy resource has no in-scope way to set one after the fact (approved resources currently only offer "retirar"/archive, never "re-edit classification" — a pre-existing gap, not introduced here).
2. **One-off backfill** (script or Cloud Function) setting `tituloVisible = nombre` on all existing `aprobado` resources.
   - Pros: Every resource "has" the field explicitly set.
   - Cons: The value written is identical to the fallback it replaces — purely cosmetic, adds a migration to write/test/run/rollback for no behavioral difference.
   - **Recommendation: 1.** Backfill only earns its cost once some future UI needs to distinguish "explicitly titled" from "never classified," and nothing in this change's scope needs that distinction.

### Recommendation

Approach 1 on every fork above. Concretely: extend `RecursoAcademico` with an optional top-level `tituloVisible`; widen `bibliotecaService.updateFicha` to persist it alongside the existing `ficha` write (no state-machine changes); move the "Recursos aprobados" grid and its selection-for-batch action out of `AsignacionesView.tsx` into `BibliotecaView.tsx`, connected back to `AsignacionesView` through a new callback that mirrors the already-proven `onRecursoAprobado`/`refreshTrigger` seam; replace the single "indexar" auto-click with: click on a `borrador`/unclassified file opens a real classification modal (reusing existing `disciplina`/`tipo`/`uso`/`tagsTexto` state and `guardarClasificacion` handler, plus new `tituloVisible` input) that on submit leaves the resource `pendiente`; a visibly separate "aprobar" action then moves `pendiente` → `aprobado` (reusing the already-tested single-click-approve path for `pendiente` resources verbatim). Delete the "Reutilizar" tab and the "Aprobado para" toggle inside the modal outright, no replacement. Skip any backfill for previously-approved resources.

This is the lowest-effort path *and* the most correct one: almost every piece of underlying machinery (state machine, service guards, model shape, the resource-list/publish callback seam) already exists and is tested: the actual net-new work is one field, one form's JSX, a component-boundary move along an already-proven seam, and deleting code that never worked.

### Risks

- **Process risk, not code risk:** every file this change must touch already has large uncommitted diffs from other in-flight (Codex/Antigravity) work under a separate governance protocol (`CIERRE CENTRO DE ESTUDIOS.md`, `COORDINACION CODEX ANTIGRAVITY - CENTRO ESTUDIOS.md`) and a still-open contract (`Plan_de_Implementación_Refactor_Modal_Programa_Académico_y_Publicar_Material.md`, pending items D14/E3-E7) that claims `AsignacionesView.tsx` as its authorized file. Recommend the user commit or at least review that WIP before layering this change on top, and update/notify via those coordination docs, since this change will edit the same file under a different initiative.
- **Test rewrite surface is real, though bounded**: several `BibliotecaView.test.tsx` cases explicitly assert today's one-click auto-classify-and-approve behavior and describe the exact behavior being replaced (not just extended) — expect edits, not pure additions, to at least 3-4 existing test cases there, plus 2-3 integration-level cases in `AsignacionesView.test.tsx`/`CentroEstudios.test.tsx` if the grid's component ownership moves.
- **The batch-publish title/tag-discard bug is real and pre-existing** (confirmed mechanically, not just observed): `publicarLote` hardcodes `titulo: ''` and omits `tags` from `asignacionBase`, and structurally cannot do otherwise today since `tituloPersonalizado`/`tagsAsignacion` are single shared values applied to a `Set` of potentially many queued resources. This change does not need to fix that publish-time path (explicitly change 2's job), but should not be mistaken for something this change accidentally introduces — it already exists on `main`'s working tree today, introduced by the very recent `asignacion-material-por-clase` change (2026-07-04).
- **No existing UI lets an admin re-classify an already-`aprobado` resource** (only "retirar"/archive is offered) — an admin who wants to retro-fit a `tituloVisible` on legacy approved resources has no path to do so within this change's scope. Worth a one-line callout to the user as a known, accepted gap rather than a silent omission.
- **Grid layout** (`vistas/CentroEstudios.tsx`'s `xl:grid-cols-[15fr_18fr_30fr_37fr]`) is hand-tuned per-column; collapsing 4 steps to 3 needs new column fractions, not just deleting a `<BibliotecaView>`/`<AsignacionesView>` pairing — small but easy-to-forget visual-regression risk.

### Ready for Proposal

Yes. Scope, model change, service change, component-boundary move, and two deletions (Reutilizar tab, "Aprobado para" in the classification modal) are all concretely identified with exact file/line anchors and a clear recommendation on every real fork. The only thing worth the user's explicit sign-off before `sdd-propose` is the process risk: this touches files under another initiative's active, uncommitted work and a still-open external contract — recommend surfacing that to the user as a heads-up/coordination step, not a blocker.
